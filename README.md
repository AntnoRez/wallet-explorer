# Wallet Explorer

Веб-приложение для визуализации движения криптовалютных средств. Вводишь адрес
кошелька → видишь граф транзакций (откуда пришли деньги, куда ушли) → кликаешь
по узлам и раскрываешь граф дальше → эвристика подсвечивает подозрительные
паттерны (дробление средств между множеством адресов за короткий срок).

**Шесть сетей: Tron, Ethereum, Polygon, Arbitrum, Solana, TON.** Четыре
семейства, общая схема данных — добавление сети внутри знакомого семейства
стоит одной записи в справочнике.

Граф работает в режиме расследования: узлы можно закреплять, и они остаются
на месте, пока ты идёшь по цепочке дальше.

## Архитектура: откуда берутся данные

**Наш сервер не читает блокчейн.** Он работает как прокси с кэшем поверх TronGrid.

```
   Браузер                Наш backend              TronGrid API            Tron
  (React)                (Node/Express)           (чужой сервис)        (блокчейн)
     |                         |                         |                    |
     |  GET /api/wallet/...    |                         |                    |
     |------------------------>|                         |                    |
     |                         | 1. есть в кэше свежее?  |                    |
     |                         |    (Postgres)           |                    |
     |                         |                         |                    |
     |                         |  ДА -> отдаём из БД     |                    |
     |<------------------------|                         |                    |
     |                         |                         |                    |
     |                         |  НЕТ -> запрос          |                    |
     |                         |------------------------>|                    |
     |                         |                         | (своя копия цепи,  |
     |                         |                         |  проиндексированная|
     |                         |                         |  <---------------- |
     |                         |    JSON со списком tx   |                    |
     |                         |<------------------------|                    |
     |                         | 2. upsert в Postgres    |                    |
     |                         | 3. агрегация + эвристика|                    |
     |   JSON: узлы + рёбра    | ЭВРИСТИКА - проверка на |                    |
     |<------------------------| подозрительность        |                    |
```

### Почему через TronGrid, а не напрямую в блокчейн

Прямое подключение к узлу сети даёт только «дай блок №N» или «дай баланс
адреса». Вопроса **«покажи все транзакции адреса»** в протоколе нет — это не
запрос, а результат индексации: нужно перебрать всю цепь и выписать, где
встречается адрес. TronGrid это уже сделал.

То есть TronGrid — не «источник блокчейна», а **индексатор**. Мы пользуемся
его индексом.

### Зачем нужен свой backend, если можно дёргать TronGrid прямо из React

1. **API-ключ.** Из фронта ключ уедет в JS-бандл и его заберёт любой желающий.
2. **Кэш.** Раскрытие графа на 20 узлов = 40 запросов. Без кэша лимит сгорит
   за минуты. Postgres здесь — щит перед лимитом API.
3. **Своя логика.** Эвристика, склейка TRX с токенами, агрегация.

### Роль Postgres

Не источник правды о блокчейне (правда — в сети, слепок — у TronGrid), а:

- локальный кэш транзакций;
- хранилище наших собственных данных: метки адресов, флаг `isSuspicious`,
  время последней синхронизации.

## Поток обработки запроса

```
1. GET /api/wallet/tron/TR7NH...
        |
2. валидация адреса (base58 + checksum)
        |
3. смотрим Address в БД
        |
        +-- lastFetchedAt свежий (< CACHE_TTL_MINUTES) --> в TronGrid НЕ идём, к шагу 7
        |
        +-- старый или адрес незнакомый
                |
4. три ПАРАЛЛЕЛЬНЫХ запроса:
        TronGrid /transactions        (TRX, фильтр type == TransferContract)
        TronGrid /transactions/trc20  (токены, берём всё)
        TronScan /api/internal-transaction  (внутренние переводы,
                                             фильтр note + rejected + result)
        |
5. нормализация: адреса -> base58, суммы -> строка, вычисление transferIndex
        |
6. upsert в БД + обновляем Address.lastFetchedAt и syncState
        |
7. ЧИТАЕМ ИЗ БД: WHERE address = ... AND timestamp > now() - GRAPH_DAYS
        |
8. строим узлы и рёбра, считаем агрегаты, гоняем эвристику
        |
9. JSON на фронт -> React Flow рисует граф
```

### Почему граф строится из БД, а не из ответа API

Принципиальный момент — шаг 7 читает **из базы**, даже если только что
записал туда данные:

- при попадании в кэш (шаг 3) ответа от TronGrid просто нет, а граф всё равно
  нужно построить — значит источник обязан быть один;
- в базе уже лежит то, что мы знали об этом адресе раньше — например,
  переводы, увиденные при разборе соседнего адреса;
- при раскрытии узлов граф накапливается: новый адрес добавляет данные,
  старые не теряются.

Если рисовать прямо из ответа API — кэш становится бессмысленным, а граф
забывчивым.

**Правило: сохраняем в БД → читаем из БД → рисуем.**

## Принятые решения и обоснования

### Кэш: что именно устаревает

Устаревают не транзакции (они неизменяемы и верны вечно), а **полнота списка**.
Сходили в 14:00, получили 50 транзакций. В 15:00 у адреса их 53. Наши 50
по-прежнему верны — просто их не все.

Поэтому `lastFetchedAt` отвечает не на вопрос «данные ещё живые?», а на
«стоит ли идти проверять, не появилось ли новых?».

**Внутри TTL мы сознательно отдаём возможно неполные данные.** Это осознанный
размен: свежесть против лимита API. Поэтому на фронте нужна кнопка «Обновить»,
пробивающая TTL.

### Как проверять актуальность данных

Узнать, актуальны ли данные, не сходив никуда, невозможно. Вопрос не «как
проверить», а «какой поход дешевле».

Рассматривались:

- **«Маячок»** — дешёвый индикатор изменений. Не годится: баланс не меняется
  при токенных переводах, счётчик исходящих не растёт от входящих. Любой
  такой индикатор иногда врёт.
- **Инкрементальный запрос** (выбрано) — просим данные начиная с последней
  известной точки. Пустой ответ = ничего нового (проверили). Непустой = уже
  и догрузили. Один запрос делает обе работы.

### Различие «запрашивали адрес» и «адрес известен косвенно»

Запросив адрес A, мы попутно узнаём адреса B и C, с которыми он
взаимодействовал. Но у B в нашей БД лежат только переводы, где он пересёкся
с A. Его собственных двухсот транзакций мы не видели.

```
Address                lastFetchedAt   что это значит
------------------------------------------------------------------
A (запрашивали)        14:00           полный список tx у нас есть
B (просто сосед)       null            знаем только tx с A
C (просто сосед)       null            знаем только tx с A
```

Без этого различия граф врал бы: кликнул на узел → «данные есть» → показали
два ребра вместо двадцати.

### Ключ сети — строка, а не числовой chainId

`chainId` — понятие исключительно EVM. У Tron его в этом смысле нет. Если
завязать первичный ключ на число, для Tron и будущих не-EVM сетей пришлось бы
выдумывать фиктивные номера.

Справочник сетей живёт в коде (`config/networks.js`), в БД летит только
строка `network`:

```
network      | chainId | family | nativeSymbol | decimals | explorer
-------------+---------+--------+--------------+----------+-------------------
tron         |  null   | tron   | TRX          |    6     | tronscan.org
eth-mainnet  |    1    | evm    | ETH          |   18     | etherscan.io
polygon      |   137   | evm    | POL          |   18     | polygonscan.com
bitcoin      |  null   | utxo   | BTC          |    8     | mempool.space
```

`family` определяет, каким провайдером добывать данные.

### Одна таблица на все сети, а не таблица на сеть

Делить надо **по модели данных, а не по сети**.

```
Tron, Ethereum, Polygon, BSC   from -> to, value, token   account-based  ОДИНАКОВЫЕ колонки
Bitcoin                        N входов -> M выходов      UTXO           ДРУГИЕ колонки
```

Tron отличается от Ethereum значениями полей (формат адреса, decimals,
провайдер API), но не набором полей. Строка таблицы выглядит одинаково.

**Отдельная таблица нужна тогда и только тогда, когда отличается набор
колонок.** Появится Bitcoin — добавим таблицы `TxInput`/`TxOutput` рядом,
существующие не тронем.

Почему не делить по сетям:

| таблица на сеть | одна таблица + network |
|---|---|
| добавить сеть = новая модель + миграция + деплой | добавить сеть = строка в `networks.js` |
| «все транзакции адреса во всех сетях» = UNION по N таблицам | обычный `WHERE address = ?` |
| N копий одной структуры, которые неизбежно разъедутся | одна модель, правка в одном месте |

Аргумент «таблица распухнет» решается не разделением: запрос всегда идёт с
`WHERE network = ?`, индекс `(network, fromAddress)` делает поиск в общей
таблице таким же быстрым. А если данных станут миллионы — есть декларативное
партиционирование Postgres (`PARTITION BY LIST (network)`), которое даёт
физическое разделение при логически одной таблице.

**Объединённую таблицу можно разбить потом. Разъединённые склеить обратно —
боль.**

Модульность нужна не в хранилище, а в коде добычи данных: `providers/tronGrid.js`,
`providers/evmEtherscan.js` — у каждой сети свой API и свои правила, но на
выходе все дают один нормализованный объект.

### Суммы — строка целого в минимальных единицах + decimals рядом

```
5 TRX      -> value="5000000"              decimals=6
1500 USDT  -> value="1500000000"           decimals=6
5 ETH      -> value="5000000000000000000"  decimals=18
```

`decimals` хранится **в самой транзакции**, а не берётся из справочника
токенов. Иначе невозможно ни отобразить сумму, ни сравнить два перевода
в эвристике. TRX — 6 знаков (не 18, как в Ethereum!), USDT-TRC20 — тоже 6.

### syncState как JSONB, а не колонки

Пагинация у разных сетей устроена по-разному: у EVM-эксплореров — по номеру
блока, у TronGrid — курсор `fingerprint`. Колонка `lastSyncedBlock` для Tron
была бы мёртвым грузом.

Решение: одно поле `syncState JSONB`, содержимое которого — **приватные данные
провайдера**. Контроллер его не интерпретирует, только хранит и отдаёт обратно.

```
Tron:  { "trx":   { "fingerprint": "TmGrm87...", "lastTimestamp": 1786542054000 },
         "trc20": { "fingerprint": "2NgPQPX...", "lastTimestamp": 1786540758000 } }
EVM:   { "lastBlock": 21000488 }
```

У каждого эндпоинта TronGrid **свой курсор** — `fingerprint` от `/transactions`
не подходит к `/trc20`. Поэтому два независимых состояния внутри одного поля.

Контракт провайдера:

```
fetchTransfers(address, syncState)  ->  { transfers, nextSyncState }
                     ^                                    |
                     +---- из БД ---------- в БД ---------+
```

Появится сеть с четвёртым видом пагинации — миграция БД не понадобится.

### Ленивая загрузка: две независимые границы

Наивная схема «всегда тянуть последние N и двигать отметку на самую свежую
запись» теряет данные. Если между обращениями к адресу случилось больше
переводов, чем влезает в лимит, середина остаётся позади и не запрашивается
уже никогда:

```
было 500 переводов, взяли 200 свежих, отметку сдвинули на новейшую
   -> 300 в середине потеряны навсегда
```

Замерено: активный кошелёк делает ~200 переводов за 20 минут — при TTL кэша
в час это не гипотетический случай.

Решение: `syncState` каждого источника хранит **две независимые границы**.

```json
{ "lastTimestamp": 1786736490000, "pendingMaxTimestamp": 1786733268000 }
```

| Поле | Смысл | Кто двигает |
|---|---|---|
| `lastTimestamp` | самая свежая известная запись | обычный запрос (идём **вверх**) |
| `pendingMaxTimestamp` | докуда дочитано вниз; `null` = промежутка нет | догрузка (идём **вниз**) |

Два режима, вызывающий код выбирает явно:

```
обычный запрос           -> что появилось нового (min_timestamp = lastTimestamp − буфер)
fetchTransfers(..., { loadMore: true })
                         -> что осталось ниже (max_timestamp = pendingMaxTimestamp)
```

Если заход упёрся в потолок страниц, `pendingMaxTimestamp` фиксирует место
остановки, и наружу выставляется флаг `hasMore` — фронт показывает кнопку
«загрузить ещё».

**Разные лимиты страниц.** Первый показ графа должен быть быстрым:

| Режим | Страниц | Замерено |
|---|---|---|
| Первый заход (`FIRST_FETCH_PAGES`) | 1 | ~0.8 сек, ~293 перевода |
| Догрузка и инкремент (`MAX_PAGES_PER_FETCH`) | 1 | ~0.8 сек, ~300 переводов |

По одной странице и на первый показ, и на каждый клик «загрузить ещё»:
шаг ровный и предсказуемый, пользователь понимает, чего ждать. При 5
страницах клик занимал бы ~33 секунды и приносил 1491 ребро — граф такого
размера всё равно нечитаем.

Замер трёх последовательных кликов:

```
заход 1:  293 перевода  0.8 сек   19:00 -> 19:50
заход 2:  304 перевода  0.8 сек   18:15 -> 19:00   строго ниже
заход 3:  305 переводов 0.6 сек   17:46 -> 18:15   строго ниже

lastTimestamp неизменен, pendingMaxTimestamp ползёт вниз
```

**Горизонт догрузки.** Глубже `GRAPH_DAYS` не копаем: показываем мы 30 дней,
значит и догонять глубже бессмысленно. Без ограничения адрес, не запрошенный
неделю, тянул бы хвост сотнями заходов.

**Кнопка «загрузить ещё» не тянет свежее.** Если у источника хвоста нет,
запрос не делается вовсе — иначе код ушёл бы вверх и подмешал новые записи.
Найдено тестом.

### Читаемость графа: четыре механизма

Замер на реальном адресе показал масштаб проблемы: **978 переводов дают 909
узлов**. Агрегация одна не спасает — адрес почти каждый раз работает с новым
контрагентом, и сжатие вышло 1.06 перевода на ребро.

| Механизм | Что делает | Результат на замере |
|---|---|---|
| Агрегация рёбер | 15 переводов A→B → одно ребро с суммой, счётчиком, периодом | 978 → 922 ребра |
| Порог значимости | Отсекает пыль и тестовые переводы (доля < 0.01% объёма токена) | −255 переводов |
| Top-N + группировка | 20 крупнейших контрагентов поимённо, остальные — в узел «+644 адреса» | 909 → 22 узла |
| Временное окно | `GRAPH_DAYS`, применяется при чтении из БД | — |

Итог: **909 узлов → 22**, граф читаем.

Сводный узел не прячет данные, а честно показывает «здесь ещё 644 связи» —
для инструмента отслеживания это важнее красоты. По клику раскрывается
следующая порция.

#### Подписи рёбер: подсказка вместо постоянного текста

Между парой адресов бывает несколько рёбер — по одному на токен. Постоянные
подписи ложились друг на друга, и от `18 746 075.52 USDT` оставался хвост
`75.52 USDT`: сумма читалась в 250 тысяч раз меньше настоящей.

Решение — показывать детали только при наведении, и сразу **все связи пары**:

```
THRvcT… ↔ TXMLo8…
   17 746 071.52 USDT   26 переводов
          379.01 TRX     1 перевод
```

Попасть курсором в линию толщиной в полтора пикселя невозможно, поэтому
поверх каждой лежит прозрачная полоса шириной 24 пикселя.

Пробовали также разводить параллельные рёбра смещением — от этого пришлось
отказаться: на графах с несколькими связями между парой рёбра переставали
отрисовываться вовсе.

#### Спам-токены на балансе

У активного адреса на балансе висят десятки токенов, которых он никогда не
касался, — на Tron рассылки массовы. Замер на тестовом адресе: **175 токенов,
из них 170 без единого перевода**.

Признак мусора — сколько раз токен участвовал в переводах этого адреса:

```
USDT   3410 переводов   настоящий
ip292     5             подделка
ip292     2             вторая подделка с тем же символом
WIN       1             спам-рассылка
NFT       1             спам-рассылка
170 токенов   0         чистый спам
```

Названию доверять нельзя: два разных контракта с символом `ip292`
показывают, что символ подделывается. Решает активность.

Символы и `decimals` берём из **своих же транзакций** — TronGrid отдаёт
баланс токена как `{адрес_контракта: сумма}`, без единого пояснения. Внешних
запросов не требуется.

Спам не выбрасываем, а прячем за раскрывающимся списком: решать за
пользователя, что ему не нужно, инструмент расследования не должен.

#### Как сравнивается значимость разных токенов

Складывать 100 USDT и 100 TRX нельзя, курсов у нас нет. Поэтому значимость
перевода — **доля от объёма своего токена** в текущей выборке. Доли
безразмерны и складываются: контрагент, забравший 30% USDT и 10% TRX,
весит 0.4.

**Поправка на распространённость токена.** Первый замер выявил перекос: NFT
с единственным переводом получил вес 1.0 (он же 100% объёма своего токена)
и вытеснил из топа реальные движения USDT. А NFT-спам на Tron массовый.

Лечится домножением на долю токена в общем потоке:

```
NFT:   доля 1.0    ×   1/978  = 0.001
USDT:  доля 0.115  × 670/978  = 0.079   <- выше, и это правильно
```

После правки NFT-отправитель ушёл в сводный узел.

### Баланс: отдельный запрос, а не сумма переводов

Из истории переводов баланс **не вычисляется**, даже если она полная. Мимо
списка транзакций проходят:

- комиссии за энергию и пропускную способность;
- заморозка TRX под ресурсы (`frozenV2`);
- награды, делегирование ресурсов;
- внутренние переводы, которых TronGrid не отдаёт.

Сумма переводов — это сальдо переводов, и оно всегда расходится с
реальностью.

Источник — `GET /v1/accounts/{address}`:

```
balance:  102204926166 SUN   -> 102 204.93 TRX (свободный)
frozenV2: [...]              -> замороженное под энергию и TRON Power
trc20:    [ {"TXGFpNx9...": "266664000000"}, ... ]   175 токенов
```

Поэтому ленивая загрузка на баланс никак не влияет: он актуален всегда.

**Нюанс:** у балансов токенов нет ни символа, ни `decimals` — только адрес
контракта и сумма. Подтягиваем из своих же транзакций по
`tokenContractAddress`; для незнакомых токенов показываем сырое значение.

**В БД баланс не храним** — устаревает в момент записи.

### Реорганизации цепи

Последние блоки не окончательны: цепь может откатиться, и сохранённая
транзакция может исчезнуть или переехать. Наша БД об этом не узнает, потому
что мы запрашиваем только то, что после сохранённой точки.

У Tron блок считается необратимым после ~19 подтверждений суперпредставителей
(~57 секунд). Решение: при инкрементальной догрузке отступаем назад на
`REORG_BUFFER_SECONDS` (60) и перезапрашиваем этот отрезок. Upsert перезапишет
изменившееся — поэтому upsert обязателен, не insert.

### Выбор сети в интерфейсе: автоопределение family + разведка

Пока сеть одна, пользователь её не указывает — фронт подставляет
`DEFAULT_NETWORK`, в UI только поле адреса.

Переключателя сетей **перед вводом не будет**. Обсуждали и отказались:
формат адреса сам говорит, к какому семейству он относится.

```
ввёл T...    -> Tron, ничего не спрашиваем (base58check однозначен)
ввёл 0x...   -> family = evm, но КАКАЯ именно сеть — неизвестно
```

**Ключевой факт: сеть не является свойством адреса.** Адрес EVM выводится
из приватного ключа одинаково в Ethereum, BSC, Polygon, Arbitrum и Base,
поэтому один и тот же `0xABC…` существует во всех этих сетях
**одновременно**, и в каждой у него своя история переводов. Это не
коллизия, а нормальная практика: люди сознательно используют один адрес
везде. Значит по адресу `0x…` определить сеть невозможно в принципе — можно
определить только семейство.

Отсюда решение: **разведка перед загрузкой.**

```
ввод 0x28C6c06298d514…
        │
        ├─ РАЗВЕДКА: по два лёгких запроса на сеть (limit=1)
        │
        ▼
   ┌────────────────────────────────────────────┐
   │  BSC       ● активен, последний перевод 2д │ ← выбран по умолчанию
   │  Ethereum  ● активен, последний  4 мес     │
   │  Polygon   ○ пусто                         │
   │  Arbitrum  ○ пусто                         │
   │  Base      ● активен, последний 11д        │
   └────────────────────────────────────────────┘
        │
        ▼
   ПОЛНЫЙ ПАРС только выбранной сети
```

**Почему не парсить все сети сразу.** Полный парс одной сети — три запроса
(нативные, токены, внутренние). Пять сетей = 15 запросов на один ввод
адреса, при бесплатном лимите Etherscan 5 rps это три секунды минимум.
Типичный адрес живёт в одной-двух сетях, остальные вернут пустоту — платим
за пять, используем одну. Хуже другое: **это замедлило бы раскрытие узлов**,
а именно им пользуются постоянно. При клике по контрагенту разведка не
повторяется — остаёмся в выбранной сети.

**Почему разведка — два запроса на сеть, а не один.** Запрос только
нативных переводов (`txlist`) пропустит адрес, который лишь получал токены
и ничего не отправлял: у такого `txlist` пустой, хотя USDT на нём лежит.
Это ровно депозитные адреса, то есть то, что мы и ищем. Поэтому
`txlist` + `tokentx`, оба с `limit=1`.

**Кэш разведки — сутки.** «В каких сетях адрес активен» меняется редко, а
без кэша каждый возврат к адресу снова стоит десять запросов.

**Не проверено:** отдаёт ли Etherscan V2 данные по нескольким `chainid`
одним запросом. Если такой эндпоинт есть, разведка схлопнется в один вызов.
Проверить по документации, когда будет ключ.

На серверный код всё это почти не влияет: `network` уже присутствует в URL,
в первичных ключах и в справочнике сетей.

Первый шаг сделан с обеих сторон: `parseUserInput()` в
`normalize/tronAddress.js` и в `normalize/evmAddress.js` отличают «это адрес
другой сети» от «это мусор» и выдают разные сообщения.

### Retention: старое из БД не удаляем

- Транзакции неизменяемы, они не устаревают.
- Удалив, обречены качать заново, тратя лимит. Кэш, который сам себя стирает,
  — не кэш.
- Объём ничтожен: 250 строк на адрес, 1000 адресов ≈ десятки мегабайт.

Фильтр по времени применяется **при чтении** (`GRAPH_DAYS`), а не при
сохранении. Причина: пользователь может передумать и попросить «за год», и
данные уже должны лежать. Фильтруй мы при сохранении — пришлось бы качать
заново.

**Правило: храним максимум, фильтруем на чтении. Обратный порядок необратим.**

## Схема базы данных

### Address

| Поле | Тип | Комментарий |
|---|---|---|
| `network` | STRING | Часть PK. Ключ из `config/networks.js` |
| `address` | STRING | Часть PK. Каноническая форма (для Tron — base58) |
| `label` | STRING(128), null | «Binance Hot Wallet» и т.п. |
| `lastFetchedAt` | DATE, null | `null` = адрес известен только косвенно |
| `syncState` | JSONB, null | Приватные данные провайдера (курсоры) |
| `isSuspicious` | BOOLEAN | Результат эвристики |
| `suspicionReason` | STRING(256), null | Почему помечен — текст для подсказки в UI |

**PK:** `(network, address)` &nbsp;&nbsp; **Индекс:** `(network, lastFetchedAt)`

### Transaction

| Поле | Тип | Комментарий |
|---|---|---|
| `network` | STRING | Часть PK |
| `hash` | STRING | Часть PK. `transaction_id` / `txID` |
| `transferIndex` | STRING | Часть PK. См. ниже |
| `fromAddress` | STRING | Каноническая форма |
| `toAddress` | STRING, null | |
| `value` | DECIMAL(78,0) | Минимальные единицы, целое. Драйвер `pg` отдаёт **строкой** |
| `decimals` | INTEGER, **null** | TRX и USDT-TRC20 = 6. `null` = неизвестен, подставлять дефолт нельзя |
| `tokenSymbol` | STRING(32), null | `null` = нативная монета |
| `tokenContractAddress` | STRING(64), null | |
| `transferType` | ENUM | `native` \| `token` \| `internal` — из какого источника запись |
| `blockNumber` | BIGINT, null | У Tron уже за 85 млн |
| `blockTimestamp` | DATE | UTC. Из `block_timestamp` (миллисекунды!) |
| `createdAt` / `updatedAt` | DATE | Когда **мы** загрузили запись — не путать с `blockTimestamp` |

**PK:** `(network, hash, transferIndex)`

**Индексы:** `(network, fromAddress, blockTimestamp)`,
`(network, toAddress, blockTimestamp)`, `blockTimestamp`, `(network, hash)`

Время входит в составные индексы намеренно. Основной запрос графа —

```sql
WHERE network = ? AND (fromAddress = ? OR toAddress = ?) AND blockTimestamp >= ?
```

С индексами только по `(network, address)` планировщик брал индекс по времени
и фильтровал адрес **перебором** — то есть на большой таблице читал бы всё
за 30 дней ради сотни нужных строк. Проверено через `EXPLAIN`:

```
было:  Bitmap Index Scan on transactions_block_timestamp   cost=88.66
       Filter: (fromAddress = ... OR toAddress = ...)      ← перебор

стало: BitmapOr                                            cost=17.97
         -> Bitmap Index Scan on ..._from_address_block_timestamp
         -> Bitmap Index Scan on ..._to_address_block_timestamp
```

Порядок колонок важен: сначала равенства, потом диапазон. Обратный порядок
сделал бы индекс бесполезным для фильтра по адресу.

Поле названо `blockTimestamp`, а не `timestamp`, чтобы не путать со временем
загрузки: транзакция могла произойти год назад, а в нашей базе появиться
сегодня.

`transferType` нужен и для отладки («откуда взялось это ребро»), и для
фильтрации на фронте.

### Ассоциаций Sequelize (belongsTo / hasMany) нет — намеренно

1. **Ключи составные.** Связь `Transaction → Address` идёт по паре
   `(network, fromAddress)`, а Sequelize умеет только один `foreignKey`.
2. **Внешний ключ мешал бы.** Разбирая транзакции адреса A, мы узнаём адреса
   B и C. При FK пришлось бы вставлять их в `addresses` **до** вставки
   переводов — иначе нарушение ограничения. База диктовала бы порядок
   операций там, где он не важен.

Связь выражается в запросах: `WHERE network = ? AND fromAddress = ?`.
По индексам это так же быстро, а гибкости больше.

### Про transferIndex — зачем он вообще

Одна транзакция может содержать несколько токен-переводов (свап, мультисенд).
Тогда `/trc20` вернёт несколько записей с **одинаковым** `transaction_id`.
PK по одному только `hash` терял бы все переводы кроме одного.

В Ethereum для этого есть `logIndex`. **В ответе TronGrid `/trc20` такого поля
нет.** Приходится выкручиваться.

```
transferIndex = "h:" + sha256(from|to|token|value).slice(0,16)   — обычный случай
              = "e:" + event_index                              — при коллизии
              = "e:0"                                           — для TRX-переводов
              = "i:" + internal_hash                            — внутренние переводы
```

**Аварийная ветка.** Если коллизия есть, а `/events` недоступен (сеть, лимит,
удалённая транзакция), совпавшие ключи разводятся суффиксом:
`h:abc`, `h:abc#1`, `h:abc#2`.

Суффикс зависит от порядка записей в ответе API, а он не гарантирован — при
повторной синхронизации возможен дубль. Это осознанный размен: без суффикса
вторая запись **гарантированно** затирает первую по первичному ключу.
Лишнее ребро в графе заметно и исправимо, потерянное — нет.

Найдено тестом: до правки фолбэк возвращал два одинаковых ключа, и запись
терялась именно там, где мы её защищали.

Замерено на живых данных: из 200 записей `/trc20` — 166 уникальных транзакций,
3 многопереводные (~2%), одна содержит **22 перевода** (мультисенд).
Реальных коллизий — **0 из 3**: хэш справляется, дозапрос `/events` нужен
действительно редко. Но без `transferIndex` мы потеряли бы 21 перевод из 22.

Алгоритм при обработке страницы:

```
1. группируем записи по transaction_id
2. считаем ключи hash(from, to, token, value) внутри группы
3. все уникальны       -> берём хэш, 0 доп. запросов   (~99.9% случаев)
4. есть повтор         -> запрос /v1/transactions/{id}/events
5. tx задела границу страницы -> тоже запрос events (страховка)
```

**Хэш мы считаем сами** — в ответе TronGrid никакого хэша перевода нет, есть
только `transaction_id` (общий для всех переводов транзакции). Хэш сворачивает
четыре поля в короткую строку фиксированной длины, пригодную для PK.

**Почему при коллизии берём `event_index`, а не свой счётчик по порядку.**
Счётчик привязан к позиции в массиве: если TronGrid вернёт те же две
одинаковые записи в другом порядке, номера разъедутся и в БД появятся дубли.
Гарантии стабильного порядка документация не даёт.

`event_index` — позиция события в блоке, зафиксированная в блокчейне навсегда.
Она едет **внутри записи**, а не приклеена к её месту в списке:

```
счётчик:      transferIndex = индекс_в_массиве     <- мы придумали
event_index:  transferIndex = запись.event_index   <- пришло из блокчейна
```

**Важно:** при коллизии мы не переиндексируем записи из `/trc20`, а
**отбрасываем их** для этой транзакции и строим строки БД целиком из `/events`.
Иначе пришлось бы сопоставлять два списка одинаковых записей — то есть снова
по порядку.

Плата: в `/events` нет `token_info`, поэтому `symbol` и `decimals` берём из
записей `/trc20` той же транзакции по `contract_address` (у одного контракта
они одинаковы независимо от события).

## TronGrid API — факты

Проверено живыми запросами 2026-08-12. **API отвечает без ключа** (с низким
лимитом), поэтому разработку можно вести до получения ключа.

### Эндпоинты

```
GET https://api.trongrid.io/v1/accounts/{address}/transactions
GET https://api.trongrid.io/v1/accounts/{address}/transactions/trc20
GET https://api.trongrid.io/v1/transactions/{txID}/events
```

Параметры: `limit` (default 20, **max 200**), `fingerprint`, `order_by`
(`block_timestamp,asc|desc`), `min_timestamp` / `max_timestamp` (в мс),
`only_confirmed`, `only_to`, `only_from`, `contract_address` (только для trc20).

При передаче `fingerprint` остальные параметры менять нельзя.

### Что отдают

**`/trc20` — готовые плоские данные, адреса сразу в base58:**

```json
{ "transaction_id": "66cc7280...", "from": "TCC2TzYDec2Mkn...", "to": "TR7NHqje...",
  "value": "1500000000", "block_timestamp": 1786540758000, "type": "Transfer",
  "token_info": { "symbol": "USDT", "decimals": 6, "address": "TR7NHqje...", "name": "Tether USD" } }
```

`value` = 1500000000 при `decimals` = 6 → **1500 USDT**.

**`/transactions` — сырой протокол, адреса в hex:**

```json
{ "txID": "971edfda...", "blockNumber": 85290333, "block_timestamp": 1786542054000,
  "ret": [{ "contractRet": "SUCCESS", "fee": 345000 }],
  "raw_data": { "contract": [{ "type": "TriggerSmartContract",
    "parameter": { "value": { "owner_address": "418ca9ae...", "contract_address": "41a614f8...",
                              "data": "a9059cbb..." }}}]},
  "internal_transactions": [] }
```

Сумма и получатель для вызовов контрактов закодированы внутри `data`
(`a9059cbb` = селектор `transfer`). **Мы это НЕ разбираем** — тот же перевод
придёт разобранным из `/trc20`.

**`/events` — события с индексом:**

```json
{ "event_index": 0, "event_name": "Transfer", "transaction_id": "66cc7280...",
  "result": { "from": "0x185cdd47...", "to": "0xa614f803...", "value": "1500000000" } }
```

### Типы операций в `/transactions`

| Тип | Что это | Берём? |
|---|---|---|
| `TransferContract` | Перевод нативного TRX | **Да** |
| `TriggerSmartContract` | Вызов контракта (в т.ч. любой USDT-перевод) | Нет — придёт из `/trc20` |
| `TransferAssetContract` | Перевод TRC-10 токена | Позже |
| `FreezeBalanceV2Contract`, `DelegateResourceContract` | Заморозка TRX, аренда энергии | Нет — денег не двигает |
| `VoteWitnessContract` | Голосование за суперпредставителя | Нет |
| `AccountCreateContract` | Создание аккаунта | Нет |

Правило: **`/transactions` даёт TRX, `/trc20` даёт токены.** Пересечение
убираем фильтром по типу — иначе один USDT-перевод попадёт в граф дважды.

### Rate limits

Официальная документация цифры **не публикует**, прямая цитата:
*«Do not hard-code fixed limits into business logic»*. По вторичным источникам
(форум TRON DAO, Zendesk) — порядка 100k запросов/сутки и ~15 QPS с ключом,
падение до ~5 QPS при превышении суточной квоты. **Не подтверждено официально.**

Отсюда: никаких жёстких `5 req/s` в коде — только **retry с экспоненциальным
backoff на HTTP 429**.

### Почему основной источник — TronGrid, а не TronScan

У TronScan API офсетная пагинация с жёстким потолком `start + limit <= 10000`.
Для адресов бирж с историей длиннее 10k транзакций полную историю он физически
не отдаст (проверено: у контракта WTRX `total` равен ровно 10000).
У TronGrid курсорная пагинация без такого потолка.

Но одну вещь TronGrid не отдаёт вовсе — внутренние переводы. Поэтому TronScan
используется как **дополнительный** источник строго для них.

## TronScan — внутренние переводы

Единственный способ увидеть TRX, перемещённый контрактом внутри исполнения
(см. [ловушку 5](#5-внутренние-переводы-невидимы-через-trongrid-account-эндпоинты)).

```
GET https://apilist.tronscanapi.com/api/internal-transaction?address={base58}&limit=N&start=0
```

Параметры: `address` (или `block`, `contract` — минимум один обязателен),
`start` (offset), `limit`. Ключ — тот же заголовок `TRON-PRO-API-KEY`.
Потолок пагинации `start + limit <= 10000`.

Реальный ответ (успешный перевод 5.95 TRX):

```json
{ "from": "TNUC9Qb1rRpS5CbWLmNMxXBjyFoydXjWFR",
  "to": "TGnC7LMji8hBpyvZt1TTEJhVpAZ5HFyJ3r",
  "hash": "ee6dea27...",           // родительская транзакция
  "internal_hash": "8afffa59...",  // свой хэш — годится как transferIndex
  "block": 85296738, "timestamp": 1786561275000,
  "rejected": false, "confirmed": true, "result": "SUCCESS", "revert": false,
  "note": "call",
  "token_list": { "token_id": "_", "call_value": 5950361,
                  "tokenInfo": { "tokenAbbr": "trx", "tokenDecimal": 6, "tokenType": "trc10" } } }
```

Отличия от TronGrid, важные при написании провайдера:

| | TronGrid (сырой протокол) | TronScan (этот эндпоинт) |
|---|---|---|
| Адреса | hex с префиксом `41` | **base58**, нормализация не нужна |
| Сумма | `callValueInfo: [{ callValue, tokenId }]` | `token_list.call_value` плоским числом |
| `note` | hex (`"63616c6c"` = `call`) | читаемая строка |
| Состав | только VM-операции | плюс системные (делегирование ресурсов) |

`call_value` — в **SUN** (1 TRX = 1 000 000 SUN), `tokenDecimal` приходит рядом.

Первоисточник структуры — protobuf `InternalTransaction` в репозитории
tronprotocol:

```protobuf
message CallValueInfo {
  int64 callValue = 1;   // сумма в SUN; 0/отсутствует = value не передавался
  string tokenId  = 2;   // пусто = TRX, иначе TRC-10 ID
}
bytes note     = 5;      // только "call" | "create" | "suicide"
bool  rejected = 6;
```

**`transferIndex` для внутренних переводов** = `"i:" + internal_hash`. Свой
хэш есть у каждой внутренней транзакции, придумывать ничего не нужно.

Исключение: `valueInfoList` — **массив**, и внутри одной внутренней
транзакции может двигаться несколько токенов. Тогда ключи получают суффикс
`#0`, `#1` — иначе записи схлопнулись бы по первичному ключу. На живых
данных массив всегда приходил из одного элемента, поэтому обычный случай
выглядит как `i:<hash>` без суффикса.

Найдено при построчном разборе кода: та же ошибка, от которой мы защищались
в TRC-20, была занесена сюда заново.

## API

```
GET /health                                    проверка живости
GET /api/networks                              список поддерживаемых сетей
GET /api/wallet/:network/:address              граф + баланс + состояние загрузки
GET /api/wallet/:network/:address/balance      только баланс
GET /api/wallet/:network/:address/transfers    плоский список переводов
```

### Параметры графа

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `days` | 30 | Глубина выборки; `0` — всё, что есть в базе |
| `topNodes` | 20 | Контрагентов поимённо; `0` — всех |
| `minShare` | 0.0001 | Порог значимости, доля объёма токена; `0` — не фильтровать |
| `limit` | 1000 | Максимум переводов из базы |
| `refresh` | — | Игнорировать TTL кэша (кнопка «обновить») |
| `loadMore` | — | Догрузить более старые переводы (кнопка «загрузить ещё») |

### Что в ответе

```json
{
  "network": { "key": "tron", "name": "Tron", "nativeSymbol": "TRX", "explorerAddress": "..." },
  "address": "TWS1onJnNTg8tJHomceqxBxTsUB1DHh7PV",
  "balance": { "trx": { "balance": "27964667472", "frozen": "0", "decimals": 6 }, "tokens": [...] },
  "graph": { "nodes": [...], "edges": [...], "stats": {...} },
  "sync":  { "fetched": false, "saved": 0, "hasMore": true, "partial": [] },
  "query": { "days": 30, "transfersInDb": 1286, "transfersUsed": 1000 }

```

`sync.fetched` — ходили ли во внешний API или ответили из кэша.
`sync.hasMore` — остались ли более старые переводы.
`sync.partial` — источники, которые не ответили (данные неполные).
`query.transfersInDb` против `transfersUsed` — видно, что показано не всё.

### Коды ответов

| Код | Когда |
|---|---|
| 400 | Неверный адрес, неподдерживаемая сеть, мусор в параметрах |
| 404 | Неизвестный маршрут |
| 502 | Внешний источник данных недоступен — наша часть исправна |
| 500 | Всё остальное; наружу без внутренних деталей |

### Метки адресов: «Binance-Hot 1» вместо TKPJza…B4MZA

Источник — TronScan `/api/account/tag`, работает без ключа. Даёт `publicTag`
(«Binance-Hot 1», «Kucoin 4»), метки риска `redTag`/`greyTag` и поведенческие
теги (`High Balance`, `Large Trader`).

Для инструмента отслеживания разница существенная: «деньги ушли на
`TKPJza…B4MZA`» и «деньги ушли на Binance» — разные выводы.

**Почему отдельным запросом, а не в составе графа.** Метка запрашивается на
ОДИН адрес и занимает 150–1100 мс. Для двадцати узлов это до двадцати секунд
в основном пути. Поэтому:

```
0 мс     GET /api/wallet/... → граф нарисован, подписи: TKPJza…B4MZA
800 мс   POST /api/labels/tron { addresses: [...] }
~5 сек   подписи обновились: «Binance-Hot 1»
```

**Лимит TronScan — 3 запроса в секунду**, и сервис сообщает это прямым
текстом: `request rate exceeded the allowed_rps(3)`. Замерено: пять
параллельных запросов дают 429 на **всех пяти**, а не на лишних двух —
то есть параллелизм здесь не ускоряет, а обнуляет результат.

Отсюда: последовательные запросы с интервалом 350 мс (≈2.8 rps) и повтор
с backoff при 429.

**Порционная догрузка.** За один вызов подтягиваем максимум 8 новых адресов,
остальные помечаем `pending: true` и отдаём с тем, что есть. Фронт повторяет
запрос, пока `stats.pending > 0`:

```
вызов 1: 5.3с  кэш:0   загружено:8  осталось:17
вызов 2: 4.7с  кэш:8   загружено:8  осталось:9
вызов 3: 5.3с  кэш:16  загружено:8  осталось:1
вызов 4: 0.4с  кэш:24  загружено:1  осталось:0
```

Без порций те же 25 адресов занимали 29 секунд одним ожиданием — и часть
запросов отбивалась по лимиту.

**Кэш в базе, а не в памяти** (в отличие от баланса): метка «Binance-Hot 1»
не меняется годами, а биржевые адреса встречаются в каждом втором графе.
TTL — неделя, потому что адрес могут пометить как скам после инцидента.

Поле `labelFetchedAt` отличает «метки нет» от «ещё не спрашивали» — иначе
мы дёргали бы TronScan при каждом появлении обычного кошелька, а таких
большинство.

**Неудачный запрос не сохраняется:** при ошибке `labelFetchedAt` не
обновляется, иначе мы запомнили бы сбой на неделю.

**Чужие метки риска хранятся отдельно от наших выводов.** `tags` — мнение
TronScan, `isSuspicious` + `suspicionReason` — результат нашей эвристики.
В интерфейсе это разные значки: «мы обнаружили паттерн дробления» и
«TronScan считает адрес подозрительным» — разные утверждения.

### Кэш баланса в памяти

Замер показал: при попадании в кэш переводов всё локальное укладывается
в 91 мс, а запрос баланса занимает от 500 мс до 8 секунд — TronGrid без
ключа отвечает непредсказуемо. Время ответа определял именно он.

Баланс кэшируется в памяти на 60 секунд (в базу не пишется — он устаревает
в момент записи). Результат: **650 → 136 → 94 мс** на повторных запросах.

Плюс отдельный эндпоинт `/balance`: фронт может показать граф сразу, а
баланс подтянуть следом.

## Эвристика дробления средств

Дробление (structuring) — крупную сумму разбивают на много мелких переводов,
чтобы не привлекать внимания. На графе выглядит как звезда: из одного адреса
веером расходятся почти одинаковые суммы за короткий срок.

### Правило

Серия считается подозрительной, если **все** условия выполнены:

| Условие | Значение | Почему так |
|---|---|---|
| Переводов в окне | ≥ 3 | Два перевода — совпадение |
| Окно | 1 час, скользящее | Фиксированная сетка «каждый час с нуля» разрезала бы серию пополам |
| Разных получателей | ≥ 3 | Три перевода одному адресу — просто три перевода |
| Разброс сумм | ≤ 15% от среднего | Строже — упустим округление «на глаз», мягче — начнём ловить обычную торговлю |
| Средняя сумма | ≥ 0.01 единицы токена | Ниже начинается пыль |
| Направление | только исходящие | Дробление — про увод средств |
| Токены | не смешиваются | 100 USDT и 100 TRX — разные величины |

Считается при синхронизации адреса, результат пишется в `isSuspicious` и
`suspicionReason`.

### Найденный баг: проверка окна целиком

Первая версия проверяла на однородность **всё окно**. Один сосед с другой
суммой ронял всю находку — а рядом с серией почти всегда что-то есть.

Симптом был характерный: на синтетике всё работало, на живых данных —
**ноль срабатываний при 41 адресе**, хотя у пятнадцати из них были явные
серии. Причём результат зависел от порядка:

```
шум ПОСЛЕ серии   → не найдено
шум ДО серии      → найдено      (окно его просто не захватило)
шум ВОКРУГ серии  → не найдено
```

Исправлено: ищем однородную группу **внутри** окна. Каждый перевод по
очереди берётся за образец, вокруг него собираются близкие по сумме,
побеждает самая многочисленная группа.

После правки — 9 адресов из 41:

```
26 переводов почти равными суммами (~142.15 USDT) на 26 адресов за 55 мин.
25 переводов почти равными суммами (~51.95 USDT)  на 25 адресов за 14 мин.
 5 переводов почти равными суммами (~2600 USDT)   на  5 адресов за  1 мин.
```

### Что это НЕ значит

Пороговое правило ловит **паттерн**, а не намерение. Точно так же выглядят
выплаты зарплат, раздачи наград и работа платёжных шлюзов. Поэтому:

- результат подписан причиной, которую можно проверить самому;
- метка хранится отдельно от чужих меток риска (`tags` от TronScan);
- формулировка — наблюдение, а не приговор.

## Фильтры выборки

| Фильтр | Значения | Что меняет |
|---|---|---|
| Период | 7 / 30 / 90 дней / всё | Глубина выборки из базы |
| Узлов | 10 / 20 / 50 / 100 | Сколько контрагентов показать поимённо |
| Мелкие переводы | скрыть / показать | Порог значимости 0.01% объёма токена |

Все три меняют серверную выборку, поэтому каждое переключение
перезапрашивает граф. Локально отфильтровать нельзя: top-N отбирается до
отправки, и «показать 50 узлов» — это другая выборка, а не другой показ.

Двойной клик по сводному узлу «+N адресов» удваивает количество показанных
узлов: свёрнутые контрагенты не пропали, они просто не попали в top-N.

### Фильтры в таблице переводов

Их два, и работают они по-разному:

| Фильтр | Где считается | Почему так |
|---|---|---|
| Направление | на клиенте | Данные уже загружены, переключение должно быть мгновенным |
| Токен | **на сервере** | Страница ограничена лимитом, и отбор на клиенте показывал бы «USDT: 16 переводов» там, где их в базе 2989 |

Фильтр по токену передаётся АДРЕСОМ КОНТРАКТА, а не символом: символы
неуникальны — у одного тестового адреса нашлось два разных контракта
с символом «ip292». Для монеты сети зарезервировано значение `native`.

Список токенов берётся из баланса, где у каждого есть счётчик переводов
по всей истории. Из загруженной страницы его собирать нельзя — предложили
бы фильтровать по тому, что случайно попало в начало.

## Сети и провайдеры

Три семейства. Внутри семейства сети отличаются одной записью в
`config/networks.js`, между семействами — отдельным провайдером.

```
family: tron     providers/tronGrid.js + tronScan.js     Tron
family: evm      providers/evmEtherscan.js               Ethereum, Polygon, Arbitrum
family: solana   providers/solanaHelius.js               Solana
family: ton      providers/tonApi.js                     TON
```

### Кто чем занимается

| Сеть | Источники | Особенность |
|---|---|---|
| **Tron** | TronGrid (`/transactions`, `/trc20`) + TronScan (внутренние) | Единственная, где нужны ДВА сервиса: внутренние переводы TronGrid не отдаёт вовсе |
| **Ethereum, Polygon, Arbitrum** | Etherscan V2, `chainid` параметром | Один ключ и один эндпоинт на все EVM-сети |
| **Solana** | Helius Enhanced Transactions | Разбирает транзакции за нас: обычный RPC связывает с кошельками только 75% переводов |
| **TON** | tonapi, события адреса | Тоже отдаёт разобранные действия, причём вместе с символом жетона и точностью |

### Почему именно эти сети

**Polygon вместо BSC.** Изначально второй сетью выбрали BSC — дешёвые
переводы, картина как в Tron. Но **на бесплатном тарифе Etherscan BSC
закрыт**, как и Base, Optimism и Avalanche. Из открытых по профилю ближе
всего Polygon.

**Solana** — самая большая дыра в покрытии после Tron и EVM: огромный
объём USDC/USDT и много розничных переводов.

**TON** — следующая по объёму стейблкоинов, растёт быстро.

**Ethereum** держим, хотя граф там своеобразный: основной объём — DeFi,
и картинка тяготеет к звезде вокруг Uniswap и мостов.

### Что можно добавить дальше

```
одной строкой   Linea, Gnosis, Blast, Mantle, opBNB и ещё два десятка
                (открыты на бесплатном ключе, но движения средств там мало)

за деньги       BSC, Base, Optimism, Avalanche — тариф Etherscan от $199/год

через Blockscout    Base и Optimism — бесплатно, API в стиле Etherscan,
                    причём с logIndex, которого нет у Etherscan V2.
                    Проверено запросами, нужна доработка EVM-провайдера

новым провайдером   Bitcoin — ломает схему БД: там нет счетов, есть UTXO,
                    нужны отдельные таблицы
```

### Метки адресов есть только у Tron

TronScan отдаёт публичную разметку («Binance-Hot 1») бесплатным
эндпоинтом. У Etherscan, Helius и tonapi такого нет, поэтому в остальных
сетях узлы подписаны сокращённым адресом.

`labelService` для сетей без TronScan сразу отдаёт то, что лежит в базе,
не делая запросов. Это важно: через тот же ответ уходит результат нашей
эвристики, и пропуск адресов погасил бы подсветку подозрительных узлов.

## Helius (Solana) — факты

Проверено живыми запросами 23–24.08.2026.

### Почему не публичный узел

Публичный RPC (`api.mainnet-beta.solana.com`) работает, но для дела не
годится:

```
                          публичный RPC   Helius
история отдаётся            14 из 30       30 из 30
запросов подряд до отказа        8         отказов нет
```

Публичный узел хранит только недавнюю историю: на старые подписи он
отвечает `null`, и половина транзакций просто не приходит.

### Почему не обычный RPC, а Enhanced API

У Solana **нет эндпоинта «переводы адреса»**. Штатный путь — взять список
подписей и запросить каждую транзакцию, разбирая инструкции. Мы этого не
делаем: разбирает Helius.

```
разбор через RPC          75% переводов удаётся связать с кошельками
Enhanced Transactions    100% (454 перевода из 454 на двух адресах)
```

Разница — в токен-аккаунтах. У владельца отдельный счёт на каждый токен,
и в инструкциях стоят именно счета, а не кошельки. Сопоставление лежит
в балансах транзакции, но там есть **не все** счета: закрытые внутри той
же транзакции отсутствуют, и дозапросом их не достать — `getMultipleAccounts`
вернул ноль из девяти.

Enhanced API отдаёт `fromUserAccount` и `toUserAccount` сразу.

### Что приходит

| Наше поле | Откуда |
|---|---|
| `hash` | `signature` |
| `fromAddress` / `toAddress` | `fromUserAccount` / `toUserAccount` |
| `value` | `accountData[].tokenBalanceChanges[].rawTokenAmount` — **не** `tokenAmount` |
| `tokenContractAddress` | `mint` |
| `decimals` | `rawTokenAmount.decimals` |
| `blockTimestamp` | `timestamp`, в секундах |
| `blockNumber` | `slot` |

Бонусом приходит тип транзакции: `SWAP`, `TRANSFER`, `CREATE_POOL` —
пригодится, если захотим отличать торговлю от переводов человек-человеку.

### Символы токенов приходится добывать отдельно

Enhanced API отдаёт только `mint`. Без символа в графе висели бы
неразличимые хэши вместо USDC, поэтому символы берём методом
`getAssetBatch` (DAS) и держим в памяти: у токена они не меняются.

Кэш ограничен пятью тысячами записей — у Solana спам-токенов на порядок
больше, чем в других сетях, и без потолка карта росла бы всю жизнь
процесса.

### Пагинация и замеры

```
100 транзакций за запрос, дальше курсором before
ход вверх — параметр until
фильтра по дате НЕТ: горизонт GRAPH_DAYS применяем на своей стороне

5 запросов за 9 секунд, отказов нет
бесплатный тариф: 100 000 кредитов, карта не нужна
```

### Ключ обязателен

`HELIUS_API_KEY` в `.env`. Тот же ключ открывает и Enhanced API
(`api.helius.xyz`), и обычный RPC (`mainnet.helius-rpc.com`) — второй нужен
для балансов и метаданных токенов.

Одна тонкость: `api.helius.xyz` стоит за Cloudflare, и тот блокирует
запросы по заголовкам. Python-скрипт получал `403 error code: 1010`,
а `curl` и `axios` проходят нормально.

## tonapi (TON) — факты

Проверено живыми запросами 25.08.2026.

### Почему tonapi, а не toncenter

Оба живые и оба без ключа отвечают. Разница в том, что tonapi отдаёт
**разобранные действия**, а toncenter — сырые сообщения:

```
tonapi       /accounts/{addr}/events -> actions: TonTransfer, JettonTransfer
             у каждого действия сразу sender.address, recipient.address,
             amount, jetton.{symbol, decimals}

toncenter    /transactions  (сообщения)  +  /jetton/transfers  (жетоны)
             символы токенов пришлось бы искать отдельно
```

Та же логика, что с Helius для Solana: чужой разбор лучше своего, если он
полный.

Бонусом приходит флаг `is_scam` — у остальных API такого нет.

### Что приходит

| Наше поле | Откуда |
|---|---|
| `hash` | `event_id` |
| `fromAddress` / `toAddress` | `sender.address` / `recipient.address` |
| `value` | `amount` |
| `tokenSymbol`, `decimals` | `jetton.symbol`, `jetton.decimals` |
| `tokenContractAddress` | `jetton.address` |
| `blockTimestamp` | `timestamp`, в секундах |
| `blockNumber` | `lt` — логическое время |

Остальные типы действий (`SmartContractExec`, `ContractDeploy`,
`NftItemTransfer`) средств между кошельками не двигают и пропускаются.

### Замеры

```
пагинация     курсор before_lt, до 100 событий за запрос
фильтра по дате НЕТ: горизонт GRAPH_DAYS применяем на своей стороне

без ключа     429 приходит на одиннадцатом запросе подряд
с ключом      то же самое: тариф даёт около запроса в секунду
с паузой 1.1 с — 8 из 8 проходят
```

Лимит считается на ключ, а не на соединение, поэтому запросы выстроены
в общую очередь — параллельные обращения из разных мест кода вместе
упрутся в тот же предел.

### Ключ

`TONAPI_KEY` в `.env`, получается на tonconsole.com. Формально
необязателен, но без него лимит ещё жёстче.

## Расследование: закрепление и цепочка

Граф работает не как просмотр одного адреса, а как инструмент трассировки.
Модель простая: **закреплённые узлы — скелет, соседи текущего узла —
рабочая область.**

```
1. Открыл адрес           он закрепляется сам: это начало цепочки
2. Двойной клик по узлу   перешёл к нему, его соседи на экране,
                          прежние соседи ИСЧЕЗЛИ — хаоса нет
3. Нашёл интересный?      «Закрепить» в правой панели
4. Пошёл дальше           закреплённые остаются, цепочка растёт
5. Нужна развилка?        двойной клик по любому узлу цепочки —
                          снова видны его соседи, закреплённое цело
```

На экране всегда ровно один временный слой плюс закреплённое — поэтому
после десяти шагов картинка остаётся читаемой.

### Кэш помнит больше, чем показано

Стор копит ВСЁ увиденное, а на экран попадает подмножество: закреплённые
плюс соседи текущего узла. Отсюда приятное следствие: **ребро между двумя
закреплёнными появляется само**, как только оба оказались на экране, —
даже если увидели мы их в разное время и из разных запросов.

Это именно то, ради чего расследование и ведётся: видно, вернулись ли
деньги туда, откуда вышли.

### Раскладка

Стороны считаются от ТЕКУЩЕГО узла, а не от начала координат:

```
        прислали                      отправили

     (A) ───┐                      ┌───► (D)
            │        ┌───┐         │
     (B) ───┼──────► │ ВЫ│ ───────┼───► (E)
            │        └───┘         │
     (C) ───┘          ▲▼          └───► (F)
                    (G) (H)  ← обмен в обе стороны
```

Закреплённые не двигаются вовсе — их координаты жёсткие. Соседи расходятся
от текущего узла, поэтому цепочка выстраивается сама: идёшь по расходам —
каждый шаг правее предыдущего.

Отдельная раскладка «по слоям» была написана и выброшена: вместе со
сторонами она боролась за одну ось, а пользы не добавляла.

**Двусторонний обмен идёт по вертикали.** Слева или справа он читался бы
как односторонний. Сторона (верх или низ) выбирается по хэшу адреса, а не
по порядку в массиве: порядок меняется между запросами, и узел прыгал бы
при каждом обновлении.

Обе связи такого узла красятся жёлтым — иначе одна была бы зелёной,
другая оранжевой, и один контрагент читался бы как два разных случая.

Связь между двумя закреплёнными — звено цепочки, красится цветом
закрепления и показывается в полную силу.

### Позиции, заданные рукой

Хранятся отдельно от расчётных и не двигаются НИКОГДА — включая центр
и начало цепочки. Пользователь, расставивший узлы, знает о своей картине
больше, чем симуляция.

Сбрасываются только при вводе нового адреса.

### Цвета

```
зелёный     прислали
оранжевый   отправили
жёлтый      обмен в обе стороны
бирюзовый   звено цепочки (оба конца закреплены)
красный     сработала эвристика или метка риска
```

## Ловушки, о которые легко споткнуться

### 1. `toLowerCase()` уничтожает Tron-адрес

```
Ethereum:  0xAb5801a7D398351b8bE11C439e05C5B3259aeC9B
           = 0xab5801a7d398351b8be11c439e05c5b3259aec9b   (hex, регистр не значим)

Tron:      TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t
           != tr7nhqjekqxgtci8q8zy4pl8otszgjlj6t          (base58, регистр ЗНАЧИМ)
```

Base58 использует заглавные и строчные как **разные символы**. Глобального
`address.toLowerCase()` в проекте быть не должно — только
`normalizeAddress(network, raw)`.

### 2. У одного Tron-адреса ТРИ представления

```
TCC2TzYDec2MknUUXLL1LveDWocceC19Qb             base58   — в /trc20, каноническая форма
41185cdd47b644f6eb30405570bfa3dfdbefe307be     hex 21b  — в raw_data (префикс 41)
0x185cdd47b644f6eb30405570bfa3dfdbefe307be     hex 20b  — в /events (EVM-стиль)
```

Все три — один адрес. Правило: `0x...` → заменить префикс на `41` → base58check.

Без нормализации в графе появятся три узла вместо одного.

Каноническая форма — **base58**: совпадает с тем, что видит пользователь и
показывает Tronscan.

Конвертацию делаем через `bs58check` (крошечный пакет), а не `tronweb`
(тяжёлый SDK ради двух функций). Писать base58check руками нельзя — легко
получить тонкую ошибку, которая всплывёт на одном адресе из тысячи.

**Побочный выигрыш:** проверка checksum даёт настоящую валидацию адреса.
Regex `^T[a-zA-Z0-9]{33}$` пропустит опечатку в середине, checksum — нет.

### 2а. Адрес Ethereum неотличим от Tron-адреса в формате `0x`

Найдено тестом при написании `tronAddress.js`.

Форма `0x...` (20 байт) из `/events` — это ровно те же байты, что и адрес
Ethereum. Различить их **невозможно в принципе**.

Последствие: наивная нормализация примет вставленный пользователем адрес
Ethereum, допишет префикс `41` и покажет граф **чужого существующего**
Tron-кошелька. Данные не те, а ошибки нет.

Решение — разделить два сценария:

```
разбор ответов API              ввод пользователя
────────────────────────        ─────────────────────────
isValid() / toBase58()          isValidUserInput() / parseUserInput()
принимают все три формата       принимают ТОЛЬКО base58

в /events других сетей нет,     0x... почти всегда означает,
двусмысленности не возникает    что человек вставил адрес Ethereum
```

Общее правило: **молча подставить не тот адрес хуже, чем отказать.**

### 2б. `keccak256` — это НЕ `sha3-256` из Node

Для EIP-55 (контрольная сумма адреса EVM) нужен keccak256. Встроенный в Node
`crypto` его **не даёт** — там только стандартизованный NIST SHA-3, у
которого другой padding и, соответственно, другой результат:

```
keccak256('')                        -> c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470
crypto.createHash('sha3-256')        -> a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a
```

Проверено замером, а не по памяти. Отсюда зависимость `js-sha3` — подменить
её встроенным `crypto` не получится, чек-суммы просто не сойдутся.

### 2в. У адреса EVM опечатку почти нечем поймать

У Tron base58check означал, что опечатка не пройдёт проверку. У EVM **любые
40 hex-символов формально валидны** — опечатка даёт другой существующий
адрес, и запрос вернёт пустой граф вместо ошибки.

Ловит только EIP-55: регистр букв выведен из `keccak256` строчной формы.

```
0x28c6c06298d514db089934071355e5743bf21d60   строчный  — контрольной суммы НЕТ
0x28C6C06298D514DB089934071355E5743BF21D60   заглавный — контрольной суммы НЕТ
0x28C6c06298d514Db089934071355E5743bf21d60   смешанный — EIP-55, проверяем
```

Поэтому `assertChecksum()` проверяет **только смешанный регистр**: адрес
целиком в одном регистре так отдаёт половина API, отвергать его нельзя.

**Честное следствие: опечатка в полностью строчном адресе не ловится
ничем.** Это свойство Ethereum, а не недоделка. Из обозревателей копируют
смешанный вид, поэтому на практике проверка срабатывает.

### 2г. Канонический адрес EVM — строчный, а не EIP-55

Канон идёт в первичный ключ и в сравнения. Etherscan отдаёт строчный вид,
обозреватель показывает смешанный, логи — как придётся. Хранили бы
смешанный — один адрес из разных источников дал бы в графе **два узла**.

Для показа человеку есть `toChecksum()`. Ссылки в обозреватель работают с
любым регистром, конверсия для них не нужна.

### 3. `block_timestamp` в миллисекундах

13 цифр, не 10. Многие блокчейн-API отдают секунды — перепутать легко,
результат: все транзакции в 1970 году.

В БД храним **UTC**, конвертируем в локальное время только при отображении.

### 4. 200 записей из `/transactions` != 200 переводов TRX

```
200 записей из /transactions
   +-- 190 x TriggerSmartContract  -> выбрасываем (это USDT, придёт из /trc20)
   +--   7 x FreezeBalanceV2       -> выбрасываем
   +--   3 x TransferContract      -> оставляем
```

У активного USDT-трейдера отфильтруется почти всё. У `/trc20` такой проблемы
нет — там все 200 записей полезные.

Если TRX-рёбер окажется стабильно мало, варианты: тянуть страницы до набора N
переводов, либо ограничивать не количеством, а временным окном.

### 5. Внутренние переводы НЕВИДИМЫ через TronGrid account-эндпоинты

Самая опасная ловушка — она не про парсинг, а про отсутствие данных.

Когда контракт пересылает TRX внутри своего исполнения (свап на DEX, вывод
из стейкинга), это **внутренняя транзакция**: у неё нет своей подписи, она
часть исполнения родительской.

Наивное предположение: «внутренние переводы придут в поле
`internal_transactions` вместе с остальными данными, надо только распарсить».
**Это неверно.**

```
/v1/accounts/{адрес}/transactions
    показывает только транзакции, где адрес — отправитель или получатель
    НА ВЕРХНЕМ УРОВНЕ (подписант либо прямой получатель)

транзакция, где адрес получил TRX только изнутри исполнения контракта,
в этот список НЕ ПОПАДАЕТ ВООБЩЕ — парсить нечего
```

Проверено: транзакция `40e4d806...`, в которой адрес
`TWS1onJnNTg8tJHomceqxBxTsUB1DHh7PV` получил 3 226 990 TRX внутренним
переводом, не находится ни в `/transactions`, ни в `/trc20` этого адреса даже
при поиске в окне ±4 секунды (ноль записей).

**Решение — третий источник:** TronScan `/api/internal-transaction`. См.
раздел [TronScan — внутренние переводы](#tronscan--внутренние-переводы).

### 5а. У внутренних переводов обязателен фильтр по `note`

Без него граф будет показывать движения, которых не было.

У обычного кошелька из 61 внутренней операции:

```
delegateResourceOfEnergy    27  <- делегирование энергии, НЕ перевод средств
unDelegateResourceOfEnergy  21  <- возврат энергии, НЕ перевод средств
call                         2  <- реальные переводы
```

**Только 2 из 61 — движение денег.** Та самая запись на 3 226 990 TRX — это
`unDelegateResourceOfEnergy`, возврат делегированного ресурса. Без фильтра в
графе появилось бы фальшивое ребро на 3,2 миллиона TRX, и эвристика
подозрительности сработала бы на пустом месте.

Протокол TRON знает только три значения `note`: `call`, `create`, `suicide`
(подтверждено protobuf-схемой `InternalTransaction` в репозитории
tronprotocol). Всё остальное, что показывает TronScan
(`delegateResourceOfEnergy` и т.п.), — системные операции с ресурсами сети,
добавленные самим TronScan.

Правило отбора:

```
берём запись, только если ВСЁ верно:
  note ∈ { "call", "create", "suicide" }
  rejected == false
  revert   == false
  result   == "SUCCESS"
  call_value > 0
```

### 5б. `token_info` может быть пустым

```json
{ "token_info": {},   <- ни symbol, ни decimals, ни адреса контракта
  "from": "TR7NHqje...", "to": "TY5uPDSy...", "value": "741940000" }
```

Без `decimals` сумма нечитаема: 741940000 — это 741.94 USDT (при 6) или
0.00000000074194 (при 18)?

Замерено: на адресах **контрактов** — до 21% записей без `decimals`
(там переводы инициирует сам контракт, и TronGrid не определяет токен).
На обычных кошельках — 0%.

Фолбэк: `decimals = null`, `tokenSymbol = null`, на фронте показываем сырое
значение с пометкой «токен неизвестен». Никогда не подставлять 6 или 18
по умолчанию — это тихо исказит суммы.

### 5в. Сумма TRX приходит ЧИСЛОМ и молча теряет точность

В `/transactions` сумма нативного перевода лежит в `amount` как **число**,
а не строка:

```json
"parameter": { "value": { "amount": 3226990000000 } }
```

`JSON.parse` превращает его в `Number`, который надёжен лишь до 2^53 ≈
9·10^15 SUN — это около 9 миллиардов TRX. При общем предложении TRX
порядка 92 миллиардов такой перевод возможен, и цифры испортились бы
**без всякой ошибки**.

Лечится перехватом ДО разбора JSON — в axios-клиенте задан
`transformResponse`, который оборачивает числовые `amount` в строки:

```js
JSON.parse(data.replace(/"amount"\s*:\s*(\d+)/g, '"amount":"$1"'))
```

В `/trc20` поле `value` и так приходит строкой — там проблемы нет.
Та же ловушка ждёт в `call_value` у TronScan.

### 5е. TronScan молча режет `limit` до 50

```
limit=20  -> получено 20
limit=50  -> получено 50
limit=100 -> получено 50   <- молча урезано
limit=200 -> получено 50
```

В документации этого нет — замерено.

Ловушка не в самом ограничении, а в его последствии: признаком «данные
кончились» служит **неполная страница**. С завышенным `limit` каждая
страница выглядит неполной, и пагинация останавливается на первой же
порции — тихо, без ошибок.

Лечится двумя способами сразу: `limit` зажат константой `PAGE_SIZE = 50`,
а конец диапазона дополнительно проверяется по полю `total` из ответа
(оно учитывает фильтр по времени — проверено: 61 запись всего, 2 за май).

### 5г. Неуспешные транзакции попадают в список

Транзакция может попасть в блок и провалиться — например, кончилась
энергия. Комиссию она заплатила, но средств не двигала.

Признак — `ret[0].contractRet`. Берём только `SUCCESS`, иначе в графе
появятся рёбра переводов, которых не было.

Отсутствие поля НЕ считаем провалом: отбрасываем только явный отказ.

### 5д. `information_schema` в Postgres отдаёт массивы вместо строк

Найдено при проверке созданных таблиц.

```
information_schema.tables:  [["addresses"], ["transactions"]]   <- массивы!
pg_tables:                  [{"tablename":"addresses"}, ...]    <- нормально
```

У колонки `table_name` специальный тип `sql_identifier`, и драйвер `pg`
разбирает его как массив. Обращение `row.table_name` даёт `undefined` —
ошибка тихая, функция просто вернёт список из `undefined`.

Для служебных запросов используем `pg_tables` / `pg_indexes` — там обычные
типы.

### 6. `environment` в docker-compose работает только при создании volume

Поменял `DB_PASSWORD` в `.env` и перезапустил — пароль не изменится, база уже
проинициализирована. Симптом: «поменял пароль, а логин не проходит».
Лечится `docker compose down -v` (удалит данные) или сменой пароля через SQL.

### 7. `docker compose down -v` стирает кэш

Без `-v` данные сохраняются. С `-v` — удаляются вместе с volume, и придётся
заново жечь лимит API.

### 8. Внутри Docker-сети порт 5432, снаружи 5433

Проброс `5433:5432` существует только для хост-машины. Adminer ходит к базе
как `postgres:5432` (по имени сервиса), не `localhost:5433`.

### 9. У `tokentx` НЕТ `logIndex` — мультипереводы неразличимы

Та же беда, что с `/trc20` в Tron (ловушка про `transferIndex`), но здесь
хуже. В ответе есть `transactionIndex` — это номер транзакции В БЛОКЕ, а не
номер перевода внутри транзакции. Одна транзакция с десятком переводов даёт
десяток записей с одинаковым ключом.

Реальный пример, Uniswap V3 Router:

```
одна транзакция = 11 переводов ERC-20, у ВСЕХ transactionIndex = 2

  transactionIndex  tokenSymbol  value
  2                 USDT         73943674726
  2                 DAI          3708913829464557701320
  2                 USDT         3710864864
  2                 WETH         1655000000000000000
  2                 DAI          3708913829464557701320   <- ПОЛНЫЙ ДУБЛЬ строки выше
  ...
```

Различить по `(hash, transactionIndex)` невозможно: 1 ключ на 11 записей.
Хэш от содержимого тоже не спасает — две записи совпадают целиком.

Масштаб: у роутера 70 из 119 транзакций содержат мультипереводы, у обычного
кошелька (Binance 8, 200 записей) — **ноль**. То есть на кошельках проблема
почти не проявляется, а на контрактах затирает данные.

Где взять настоящий `logIndex`:

```
module=logs&action=getLogs                     есть logIndex (0x9)
module=proxy&action=eth_getTransactionReceipt  есть logIndex у каждого лога
```

Оба варианта стоят дополнительных запросов. Дешевле — вести пагинацию
**по блокам**, а не по страницам: тогда транзакция не разрывается между
пачками и позиция записи в ответе становится устойчивым индексом.

### 10. `offset` молча режется до 1000

```
запросил offset=10000  ->  вернулось 1000 записей, status=1, ошибки нет
```

Ровно как TronScan режет `limit` до 50. Полагаться на запрошенное число
нельзя — считать надо фактически полученное.

### 11. Потолок глубины `page × offset ≤ 10000`

```
page=10 offset=1000  (=10000)  ->  1000 записей, OK
page=11 offset=1000  (=11000)  ->  result: null, status != 1
page=2  offset=10000 (=20000)  ->  result: null, status != 1
```

**Сообщения об ошибке нет** — приходит пустой `result`. Легко принять за
«данные кончились» и молча потерять историю. Глубже 10 000 записей идти надо
через `startblock`/`endblock`, а не через номер страницы.

### 12. `timeStamp` в СЕКУНДАХ (в Tron — в миллисекундах)

```
Etherscan:  "timeStamp": "1787201255"      10 цифр, секунды
TronGrid:   "block_timestamp": 1787201255000  13 цифр, миллисекунды
```

Общий код на две сети — прямая дорога к транзакциям в 1970 году либо
в 58000-м. Приведение к датам делает провайдер, каждый по-своему.

### 13. `txlist` полон записей с `value: "0"`

Это вызовы контрактов: сам перевод токена лежит в `tokentx`, а в `txlist`
от него остаётся оболочка с нулевой суммой.

```json
{"value": "0", "methodId": "0xa9059cbb",
 "functionName": "transfer(address _to, uint256 _value)"}
```

Один в один `TriggerSmartContract` в Tron (ловушка 4). Без фильтра
`value > 0` граф зарастёт нулевыми рёбрами.

### 14. Solana: API отдаёт транзакции, где адрес УПОМЯНУТ

Не переводы адреса, а транзакции, в списке аккаунтов которых он
встречается. Для обычного кошелька разница невелика, для адреса-пула —
полная:

```
пул PUMP_AMM   612 переводов в ответе, с его участием НИ ОДНОГО
биржевой       252 перевода, 9 из них между третьими сторонами
обычный        6 переводов, 4 своих
```

Остальные провайдеры отдают именно переводы адреса, и код выше на это
рассчитывает. Сохранив чужое, мы пометили бы адрес загруженным, не
загрузив о нём ничего, — а граф остался бы пустым без объяснения.
Поэтому чужие переводы отсеиваются в провайдере.

### 15. Solana: сумма перевода приходит числом с плавающей точкой

```json
"tokenAmount": 1608.299142                     // float — ненадёжно
"rawTokenAmount": { "tokenAmount": "-1608299142",
                    "decimals": 6 }            // строка — точно
```

Берём второе, из `accountData[].tokenBalanceChanges`. Первое совпало
с точным на всех 389 проверенных переводах, но float даёт 15–16 значащих
цифр, а у токенов с девятью знаками после запятой суммы легко выходят за
этот предел.

Ровно та же ловушка была в TronScan (5в) — второй раз наступать не стали.

### 16. Solana: подпись длиннее, чем помещалось в базу

```
Tron      64 символа   hex
EVM       66 символов  hex с префиксом 0x
Solana    88 символов  64 байта в base58
```

Колонка `hash` была `varchar(80)`, и сохранение падало с
`value too long for type character varying(80)`. Расширена до 96.

### 17. Solana: у одного токена несколько счетов у одного владельца

Баланс надо складывать ПО ТОКЕНУ, а не по счёту. На кошельке Binance
USDT встретился 15 раз, USDC 17 — это разные токен-аккаунты одного и того
же токена. Без сложения интерфейс показывал бы полтора десятка строк
«USDT» с разными суммами.

### 18. Solana: спам-токенов на порядок больше, чем в других сетях

```
Tron      174 токена на балансе, осмысленных 13
Solana   3812 токенов,          осмысленных 37
```

Полный список весил 615 КБ из 642 КБ всего ответа. Токены с переводами
отдаём все, хвост режем до полусотни и сообщаем полное число отдельным
полем — ответ похудел до 38 КБ.

### 19. Solana: контрольной суммы в адресе нет вообще

```
Tron      base58check ловит испорченный адрес
EVM       EIP-55 ловит, если регистр смешанный
Solana    любые 32 байта валидны
```

Опечатка не будет отвергнута — адрес просто окажется чужим и пустым.
Это свойство сети, обойти нечем.

Длину проверять надо В БАЙТАХ: ведущие нулевые байты кодируются
единицами и укорачивают запись. У System Program адрес из 32 нулевых
байт записан 32 символами, обычный кошелёк занимает 44.

### 20. TON: три формы одного адреса

```
0:4317566082f7afe0ce2dc97b26c08799a903e4c3808b0a7758f6508a334b4fb0   raw
EQBDF1Zggvev4M4tyXsmwIeZqQPkw4CLCndY9lCKM0tPsOLS                     bounceable
UQBDF1Zggvev4M4tyXsmwIeZqQPkw4CLCndY9lCKM0tPsL8X                     non-bounceable
```

**Это один адрес.** EQ и UQ различаются единственным байтом-флагом:
вернутся ли деньги отправителю, если контракт не смог принять платёж.
К тому, ЧЕЙ это кошелёк, флаг отношения не имеет — кошельки показывают
UQ, обозреватели и API чаще EQ или raw.

Без приведения к одной форме один человек стал бы тремя узлами. Та же
беда, что с тремя представлениями в Tron.

Канон — raw: единственная форма без лишнего флага, и именно её отдаёт
API, так что на разборе ответов конверсия не нужна.

### 21. TON: сумма монеты приходит ЧИСЛОМ, а жетона — строкой

```json
"JettonTransfer": { "amount": "1" }          // строка, точно
"TonTransfer":    { "amount": 200000000 }    // ЧИСЛО, опасно
```

У TON девять знаков после запятой, поэтому число переполнит точное целое
JavaScript на суммах свыше девяти миллионов TON. Большие числа
оборачиваются в строки ДО разбора JSON — приёмом из `tronGrid.js`.

Третий раз одна и та же ловушка: TronScan (5в), Helius (15), теперь TON.

### 22. TON: лимит около запроса в секунду, даже с ключом

```
без ключа   429 на одиннадцатом запросе подряд
с ключом    то же самое
с паузой 1.1 секунды — 8 из 8 проходят
```

Считается на ключ, а не на соединение, поэтому пауза должна быть общей
для всего процесса. Запросы выстроены в очередь, как метки TronScan
в `labelService.js`.

### 23. Ширина колонок: адреса и хэши у сетей разные

Дважды упирались в предел и дважды расширяли:

```
                Tron   EVM   Solana   TON
hash             64     66      88     64     -> varchar(96)
адрес            34     42      44     66     -> varchar(80)
```

Симптом одинаковый и неочевидный: `value too long for type character
varying(N)` при сохранении, причём сам запрос к API проходит нормально.

Заодно вскрылся рассинхрон: `tokenContractAddress` в модели стоял 64,
хотя это тот же адрес, что у кошельков.

## Перенос на другую машину

### Что НЕ едет через git — и это правильно

| | Почему | Что делать на новой машине |
|---|---|---|
| `.env` | Пароль БД и четыре ключа API: TronGrid и tonapi (необязательны), Etherscan и Helius (обязательны для своих сетей). В `.gitignore` | Скопировать вручную. Либо `cp .env.example .env` и заполнить заново — там 21 переменная с комментариями |
| `node_modules/` | 200+ МБ | `npm ci` в `server/` и в `client/` |
| Данные Postgres | Это **кэш**, а не источник данных | `docker compose up -d`, база наполнится сама при первом запросе |

`npm ci`, а не `npm install`: ставит ровно то, что в `package-lock.json`.
Оба lock-файла в репозитории.

### Порядок

```bash
git clone <репозиторий> && cd "Wallet Explorer"

# .env кладём рядом с docker-compose.yml
docker compose up -d
docker compose ps                    # postgres должен быть healthy

cd server && npm ci && npm run dev    # http://localhost:4000
cd ../client && npm ci && npm run dev # http://localhost:5173
```

Порт Postgres наружу — **5433**, не стандартный 5432. Если на новой машине
уже крутится своя база, конфликта не будет.

Схему таблиц создаёт Sequelize при старте сервера — отдельной миграции нет.

### История диалога с Claude Code не переезжает

Транскрипты хранятся **локально на диске**, не в аккаунте:

        <uuid>.jsonl     ← весь диалог

Логин привязывает доступ и оплату, но транскрипты за собой не тащит. На

### Режим работы над проектом

Зафиксировано, чтобы не объяснять заново: **один файл за раз**, после
каждого — разбор построчно, потом ревью. Не вываливать пачку файлов сразу.

Фраза «проверь построчно» означает **аудит на баги**, а не пересказ кода.
Такие проверки уже нашли: потерю заголовка `Accept`, неэффективные индексы,

пропуск граничного блока в пагинации EVM, потерю хвоста при инкременте,
несовместимое имя поля баланса и неограниченный кэш метаданных Solana.

  такую проверку негде было делать.
- **Base и Optimism через Blockscout** — бесплатно, API в стиле Etherscan
  и даже с `logIndex`. Проверено запросами, нужна доработка
  EVM-провайдера под второй транспорт.
- **BSC, Avalanche** — упираются в платный тариф Etherscan, кода почти нет.
- **TRC-10 токены** — идут внутри `/transactions` как `TransferAssetContract`.
  Объём ничтожен против USDT.
- **UTXO-сети** (Bitcoin) — ломают схему БД: там нет счетов, есть UTXO.
  Потребуют отдельных таблиц, существующие не затронут.
